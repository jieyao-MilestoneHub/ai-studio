## 1. 評測哲學

### 1.1 天花板不是 100%

Stanford *Generative Agent Simulations of 1,000 People* (arXiv:2411.10109) 的量測方法是本文件的基礎：agent 的準確率須除以**本人兩週後複測自己答案的一致率**來正規化。

該研究的實際數字：GSS 上原始準確率 65.67%，本人自我一致性 79.53%，正規化後 0.83。

**推論：本人自己隔兩週也只跟自己一致約八成。** 任何以 100% 為目標的評測都在量測一個不存在的東西。

### 1.2 分母必須先取得

自我一致性是 S1 的分母。它需要兩週的真實等待，是整條開發線上唯一無法壓縮的延遲。

**因此：§3.2 的第一輪作答為專案第 0 天工作項，先於任何訓練。**

### 1.3 少而精，跑多次

τ-bench (arXiv:2406.12045) 的明確取捨：寧可犧牲數量換品質，少量高品質任務跑多次（配 pass^k）比大量任務跑一次更能揭露真實問題。

這對免費層是好消息：30 個任務跑 8 次遠比 500 個任務跑 1 次便宜。本文件全面採用此取捨。

### 1.4 四個 suite 必須分開

三個能力互相拉扯——訓練「更主動」會直接傷害「懶得回」。混在一個總分裡量測會使歸因不可能。**MUST NOT 產生跨 suite 的加權總分。**

## 2. Suite 總覽

| ID | 名稱 | 對應目標 | 主指標 | 分母/基準 |
|---|---|---|---|---|
| S1 | 人格保真 | G1 | normalized accuracy | 本人自我一致性 |

## 3. S1 — 人格保真

### 3.1 量測對象

在本人**未曾表態過**的新情境下，孿生的判斷是否與本人一致。

MUST 為新情境。若題目答案可在訓練資料中找到，量到的是記憶不是保真。

### 3.2 資料構建

1. Teacher 自本人 held-out 時間段的資料生成 60–80 題情境題（單選或李克特量表）。
2. **Wave 1**：本人作答。記為 `R1`。
3. 等待 14 天。
4. **Wave 2**：本人重新作答同一批題。記為 `R2`。
5. 孿生作答。記為 `A`。

題型分佈 SHOULD 為：

| 類型 | 占比 | 說明 |
|---|---|---|
| 價值取捨 | 30% | 兩個都合理的選項二選一 |
| 偏好 | 25% | 工具、做法、風格的選擇 |
| 反應傾向 | 25% | 「看到 X 你會不會做 Y」 |
| 回想 | 20% | 需 `recall()` 支援，見 §3.5 |

### 3.3 指標

```
self_consistency = agreement(R1, R2)
raw_accuracy     = agreement(A, R2)
normalized_accuracy = raw_accuracy / self_consistency
```

- 比對基準 MUST 為 `R2`（與原研究一致）。
- 連續型題目 MUST 改用 normalized correlation。
- `normalized_accuracy = 1.0` 意即孿生預測本人的準確度，等同本人複製自己答案的準確度。

### 3.4 必要的 baseline

S1 MUST 同時跑以下三組，否則分數無意義：

| Baseline | 內容 |
|---|---|
| B0 | 未微調底模 + 空白 prompt |
| B1 | 未微調底模 + persona prompt（一段本人自述） |
| B2 | 未微調底模 + 訪談 transcript 注入 context |
| **T** | 孿生（LoRA + memory store） |

**若 T 未顯著優於 B2，則 LoRA 不應存在**——直接用長 context 注入 transcript 即可，成本更低。這是本專案最重要的一個 kill switch。

原研究顯示 B2 型（訪談型）優於 B1 型（persona 型）與 demographic 型，故 B2 是真正的對手，不是 B0。

### 3.5 回想題的額外規則

回想題 MUST 分別計分兩件事：

- **內容正確性**：檢索到的碎片是否為正確的那一個
- **模糊度匹配**：孿生給出的時間精度是否接近本人的表述

第二項是刻意的。本人說「大概去年夏天」時，孿生回答精確日期即為失敗，即使日期正確。

## 4. S2 — 工具使用

### 4.1 量測對象

兩件事，MUST 分開計分：

- **S2a 任務完成**：能不能把事情做完
- **S2b 風格匹配**：查了幾次、何時放棄、選了哪個工具——是否像本人

S2b 才是本專案的差異點。S2a 主要由底模決定。

### 4.2 資料構建

- 20–30 個任務，取自本人真實的工具使用情境（held-out 時段）。
- 每個任務 MUST 有可程式驗證的終局狀態（檔案內容、DB state、檢索結果集合），MUST NOT 以 LLM 判斷「有沒有做完」。
- 任務 MUST 涵蓋失敗路徑：工具回傳空結果、超時、權限錯誤。本人在這些情況下的行為（重試幾次、何時放棄）是核心訓練目標。

### 4.3 指標

```
pass^k = 同一任務獨立跑 k 次全部成功的比例
```

- MUST 回報 `pass^1` 與 `pass^4`。
- MUST NOT 只回報 `pass^1`。

理由：τ-bench 顯示即使 gpt-4o 等級的 function calling agent，任務成功率也低於 50%，且 retail domain 的 pass^8 低於 25%。單次成功的 demo 會系統性地高估可靠度。

S2b 額外指標：

| 指標 | 定義 |
|---|---|
| 工具選擇 top-1 一致率 | 首次呼叫的工具與本人相同的比例 |
| 呼叫次數 MAE | 與本人在同型任務的平均呼叫次數差 |
| 放棄點偏差 | 連續失敗幾次後停止，與本人的差 |

### 4.4 Plugin 遷移測試（驗證 SPEC C2/D16）

保留 1–2 個**訓練時完全未出現**的工具，於評測時注入。

- 通過條件：孿生對新工具的使用風格 SHOULD 與其對已知同類工具的風格一致。
- 失敗徵狀：完全不使用新工具，或使用方式與人格無關。
- 此項失敗即代表工具名稱遮蔽（SPEC §5.3）未生效。

## 5. S3 — 主動性

### 5.1 量測對象

**在無人呼叫時，判斷此刻本人會不會有動作。** 包含正確地不動作。

這是三個能力中最難的一個，也是唯一一個「做得太好」會造成對外事故的。

### 5.2 資料構建（本文件中最容易做錯的部分）

輸入為時間序列事件流。每個時點標註本人當時是否行動。

**負例選取規則（MUST）**，依據 ProAgentBench (arXiv:2602.04482)：

- 負例 MUST 選自「情境上接近真實觸發時刻、但本人實際未行動」的時點。
- 負例 MUST NOT 為無活動時段、睡眠時段、或任何 trivial negative。
- 具體到本專案：負例是「他看了那則新聞但沒發文」，不是「他那天沒上網」。

**切分規則（MUST）**：

- MUST 為 time-based split，不得隨機切分。
- 訓練集的時間 MUST 全部早於測試集，避免時間洩漏。

不遵守負例規則的後果：S3 分數虛高，但實際部署後孿生整天發廢文。這是本專案第一號失敗模式，而它**只會在 S3 資料構建錯誤時被隱藏**。

### 5.3 指標

以 confusion matrix 為基礎：

| | 本人有行動 | 本人無行動 |
|---|---|---|
| 孿生有行動 | TP | **FP** |
| 孿生無行動 | FN | TN |

```
Precision   = TP / (TP + FP)
Recall      = TP / (TP + FN)
False Alarm = FP / (FP + TN)
F1          = 2PR / (P + R)
```

- **False Alarm 為本 suite 的主要看板指標**，非 F1。
- 理由：Proactive Agent (arXiv:2410.12361) 的核心發現是模型「該幫忙時能幫忙，但不需要協助時閉不了嘴」，普遍 false alarm 偏高。F1 會把這個問題平均掉。

### 5.4 現況基準

同研究中，GPT-4o 在 ProactiveBench 上 F1 約 64.6%，微調後的 Qwen2-7B 為 66.47%（開源最佳）。

**換算為產品語言：每三次主動發言，約有一次是本人不會發的。** §7 的門檻裁決應以此為錨點。

### 5.5 不回應率校準

獨立回報一項：

```
silence_rate_delta = |孿生不回應率 − 本人真實不回應率|
```

此項針對「懶得回」這類人格特徵。模型天生偏向回應，此指標會直接暴露訓練資料負例不足。

## 6. Judge

### 6.1 配置（已裁決）

Judge MUST 為 **Claude Code**（使用既有訂閱）。MUST NOT 使用計量付費 API 進行評測。

附帶收益，MUST 保持：teacher 為 Gemini、judge 為 Claude，兩者天然跨供應商。原先「judge 與 teacher 同源導致自我確認」的風險因此自動消除。**若日後更換 teacher，MUST 確保其與 judge 非同一供應商。**

Judge MUST 不知道受測樣本來自孿生或本人。

### 6.2 執行方式（因 judge 為互動式而必要）

MUST 腳本化，MUST NOT 以對話方式逐筆詢問：

1. 評測樣本輸出為 `eval/in/<run_id>.jsonl`，來源標籤 MUST 剝除
2. Judge 讀檔，依 rubric 逐筆判定
3. 輸出 `eval/out/<run_id>.jsonl`，格式固定
4. **分數由腳本計算，MUST NOT 由 judge 給出總分或百分比**

第 4 點的理由：讓 judge 直接給總分會使結果無法重算、無法追溯到單筆、也無法在 rubric 變更後重新聚合。Judge 的職責僅限逐筆語意判定。

### 6.3 對齊驗證（MUST，先於任何 judge 結論）

1. 隨機抽 30 筆評測樣本
2. 本人親自標註
3. 計算 judge 與本人標註的 agreement
4. Agreement < 0.80 時，judge 結論 MUST NOT 被採信，須改寫 rubric 後重測

**0.80 這個數字 MUST NOT 隨 §7 的階段性標準下修。** 它是量測儀器的校準值，不是產品品質目標。下修它不會讓孿生變好，只會讓其他所有數字失去意義。

### 6.4 重跑紀律（本版新增）

Judge 改為互動式且由本人親自操作，引入了原本不存在的風險：看到分數不滿意就重跑。

- 每次 judge 執行 MUST 記錄 `run_id`、時間戳、rubric hash。
- **MUST NOT 因分數不理想而重跑同一批樣本。**
- 唯一允許重跑的條件：rubric 有變更且變更已記錄。此時 MUST 重跑**全部歷史 run**，否則跨輪比較失效。
- 非確定性處置：同一批樣本跨 session 的判定可能不同。SHOULD 對 sealed split 連跑兩次並回報差異；差異 > 5% 時，該輪結果 MUST 標記為低信心，且 MUST NOT 用於閘門升級。

### 6.5 重新驗證時機

- Judge 模型版本變更
- Rubric 修改
- 跨 session 差異 > 5%
- 每季一次

## 7. 通過門檻（已裁決）

裁決原則：**標準先設中間值，隨迭代調高。** 但門檻分為兩組，適用不同原則。

### 7.1 孿生堪用門檻（分階段，可調高）

| 指標 | T1 起始 | T2 目標 | 文獻參考 |
|---|---|---|---|
| S1 normalized accuracy | **≥ 0.70** 且 > B2 baseline | ≥ 0.78 | 0.83（訪談）／0.86（合併） |
| S2a pass^1 | **≥ 0.60** | ≥ 0.70 | — |
| S2a pass^4 | **≥ 0.35** | ≥ 0.50 | τ-bench 顯示此值普遍偏低 |
| S2b 工具選擇 top-1 | **≥ 0.60** | ≥ 0.72 | — |
| S3 False Alarm | **≤ 0.30** | ≤ 0.20 | 0.12 為 context-graph 類方法回報值 |
| S3 F1 | **≥ 0.55** | ≥ 0.65 | 0.66 為微調 7B 的 SOTA |
| S3 silence_rate_delta | **≤ 0.15** | ≤ 0.08 | — |
| S4 辨識率 | **≤ 0.75** | ≤ 0.65 | 0.50 = 完全分不出 |
| S4 code_switch_rate_delta | **≤ 0.15** | ≤ 0.08 | — |
| Judge agreement | **≥ 0.80** | 不調整 | 見 §6.3 |

- T1 全數達標即為「孿生堪用」，可進入日常使用（L0 草稿模式）。
- T1 未達標的孿生 MAY 繼續迭代，MUST NOT 進入任何自動送出級別。
- 調高 T1 至 T2 的時機由本人決定，但 MUST 於報告中記錄變更時的 run_id。

### 7.2 自動送出閘門（不適用「先放中間」）

對應 `SPEC.md` §6.5 的 L1／L2。**對外訊息不可逆，故此組門檻高於 T1 且不隨階段放寬。**

| 級別 | 條件（MUST 全數滿足） |
|---|---|
| **L1 白名單自動送出** | S3 False Alarm ≤ **0.15**；silence_rate_delta ≤ **0.10**；S1 ≥ **0.78**；且**連續兩輪** eval 皆達標 |
| **L2 全自動** | S3 False Alarm ≤ **0.10**；L1 實跑滿 **30 天**；該期間本人否決率 ≤ **0.10** |

- 升級 MUST 手動觸發並附上兩輪 eval 紀錄。
- 降級 MUST 自動：任一輪未達當前級別門檻即立刻降級（`SPEC.md` §6.5）。
- 標記為低信心的輪次（§6.4）MUST NOT 用於升級判定。

### 7.3 為什麼兩組門檻不同

T1 允許 S3 False Alarm 0.30，即**每十次主動回覆約有三次是本人不會回的**。

- 在 L0 草稿模式：無害。本人會看到並否決，而每一次否決都是高品質硬負例，直接回流訓練集。這正是低門檻起步的價值所在。
- 在 L2 全自動：不可接受。三成的錯誤訊息已直接送到對方手上。

**低門檻起步的前提是人在環。兩者是同一個設計的兩面，不可分開採用。**

## 8. S4 — 盲測

最終驗收，也最便宜。

### 8.1 程序

1. 取 held-out 時段的本人真實產出（貼文、訊息、回覆）N 則。
2. 孿生針對同樣情境產出 N 則。
3. 混合、隨機排序。
4. 由本人及 2–3 位熟識者判斷每則的來源。

### 8.2 指標

```
辨識率 = 正確判斷的比例
```

- 0.50 = 完全分不出來
- MUST 同時記錄辨識者的判斷理由。理由的分布比數字有用——它會直接指出下一輪要修的是什麼（例如「記得太清楚」指向 SPEC §4.4 遺忘機制未生效）。

### 8.3 樣本量

N ≥ 20 每類。低於此值統計上不可解讀。

### 8.4 語言與語碼轉換（本版新增，依 `SPEC.md` §11-D）

中英混用的比例、以及**在什麼情境下切換**，是強烈的人格訊號，且台灣使用者普遍存在。它不是格式問題，是身分問題。

- S4 樣本 MUST 包含本人真實的中英混用產出，MUST NOT 只取純中文樣本。
- MUST 額外回報：

```
code_switch_rate_delta = |孿生中英混用比例 − 本人真實比例|
```

- 切換情境 SHOULD 一併檢核：本人可能在技術詞彙、情緒詞、對特定對象時才切換。孿生若混用比例對但情境錯，盲測仍會被辨識出來。
- **字體規則**：除非本人真實資料中存在簡體輸出，否則孿生產出簡體即記為 S4 失分。支援簡體輸入不等於輸出簡體。

| 風險 | 規則 |

## 10. 執行成本（已依 judge 裁決改寫）

| 項目 | 資源 | 成本 |
|---|---|---|
| 孿生推論（S1–S3） | Modal scale-to-zero 或本機 | 免費層內 |
| Judge | Claude Code 既有訂閱 | 已付，不計量 |
| Teacher（產生 eval 題目） | Gemini Flash 免費層 | 遠低於單日 RPD |
| 人工（S4 盲測、§6.3 對齊 30 筆） | 本人 + 2–3 位熟識者 | 每輪約 60–90 分鐘 |

### 10.1 瓶頸已轉移

Judge 改為 Claude Code 之後，評測的限制因素**從 API 額度變成本人的時間**。這改變了執行節奏：

| Suite | 自動化程度 | 建議頻率 |
|---|---|---|
| S1、S2、S3 | 可全自動（judge 腳本化，§6.2） | **每輪訓練後 MUST 執行** |
| §6.3 judge 對齊 | 需本人標註 30 筆 | 每次 rubric 變更時 |
| S4 盲測 | 需本人 + 熟識者 | SHOULD 每 3 輪；**任何閘門升級前 MUST 執行** |

MUST NOT 只跑 S1 就宣告改善——S1 提升常以 S3 惡化為代價。

## 11. 報告格式

每輪 MUST 產生：

```
run_id, base_model, adapter_hash, dataset_hash, eval_set_version, date
S1: normalized_accuracy (T / B0 / B1 / B2), self_consistency
S2: pass^1, pass^4, tool_top1, call_count_mae, giveup_delta, plugin_transfer
S3: precision, recall, false_alarm, f1, silence_rate_delta
S4: 辨識率, 理由分布, code_switch_rate_delta
judge_agreement, judge_rubric_hash, judge_session_delta, confidence(high|low)
gate_level: L0|L1|L2
```

MUST NOT 產生跨 suite 加權總分（見 §1.4）。

## 12. 反模式清單

以下皆為已知會產生「看起來很好但實際失敗」的做法：

1. 只回報 pass^1
2. 用無活動時段當 S3 負例
3. 隨機切分而非 time-based split
4. 只跟 B0 比，不跟 B2 比
5. 用 F1 當 S3 主看板而忽略 False Alarm
6. 未驗證 judge 對齊就採信 judge 結論
7. 拿訓練資料裡出現過的情境當 S1 題目
8. S1 提升就宣告成功，不看 S3
9. 產生跨 suite 總分
10. 分數不理想就重跑同一批 judge 樣本（§6.4）
11. 讓 judge 直接給總分而非逐筆判定
12. 為了讓孿生達標而下修 judge agreement 門檻
13. 以低信心輪次（跨 session 差異 > 5%）作為閘門升級依據
14. 用 T1 的門檻決定是否開啟自動送出（§7.3）
