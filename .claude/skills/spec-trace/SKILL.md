# spec-trace — 動手前的溯源

## 這個 skill 解決的問題

目標漂移不是走錯路。是每一步都合理，加起來變成另一件事。

它有三個固定的入口：
1. 需求沒有規格依據，但聽起來很合理，所以直接做了。
2. 做的過程中發現「順手可以一起做」，所以一起做了。
3. 對話變長，原始目標退出 context，後半段在優化前半段的副產物。

這個 skill 在三個入口各設一道閘。

---

## 第一步：讀規格，不要憑印象

MUST 實際讀 `SPEC.md` 與 `EVAL.md` 的相關章節。

- MUST NOT 依賴對話中先前的摘要。摘要會漏掉「不是」條款，而 `SPEC.md` §2 的定義表明說「凡定義含『不是』條款者，該條款與定義本身同等具約束力」。
- 讀的順序：`SPEC.md` §2 名詞定義 → 對應層的規格章節 → §10 決策紀錄 → `EVAL.md` 的對應 suite。
- §10 決策紀錄最容易被略過，但它是唯一寫著「失敗徵狀」的表。**要做的事若能對應到某條決策的失敗徵狀，代表你正在做的事已經被裁決過了。**

---

## 第二步：產出溯源表

固定三欄，一列一件事。禁止把多件事合併成一列。

```
| 要做什麼 | SPEC 條號 | EVAL 觀測點 |
|---|---|---|
| 在 ingest 記錄已讀狀態 | §4.3 曝光採集、D20 | S3 硬負例比例、silence_rate_delta |
```

### 三種結果，三種處理

**A. 三欄都填得出來** → 通過，進入計畫階段。

**B. 有 SPEC 條號，但填不出 EVAL 觀測點**
→ 依 `SPEC.md` §4 開頭原則：「無法對應到任何評測項的規則不應存在於此。」
→ MUST 停下，二選一回報：(a) 補一個評測觀測點，或 (b) 這條需求應該砍掉。
→ MUST NOT 以「先做了再說，之後補測」通過。之後不會補。

**C. 填不出 SPEC 條號**
→ 這是規格缺口。MUST NOT 寫程式。
→ MUST 產出一份規格提案，格式依 `SPEC.md` §0 的三要件：

```
取捨對象：我們選了 A 而不是 B（B 是什麼，為什麼不選）
理由：____（且此理由可被什麼證據推翻）
可觀測後果：若做錯，會在 EVAL.md 的哪個指標上顯現
```

三要件缺一者，依 `SPEC.md` §0 應進 §11 阻塞清單，而非 §10。**阻塞項不得被實作依賴。**

**D. 條號落在 `SPEC.md` §11「剩餘開放項」**
→ 立即停止。回報這是阻塞項，需要裁決而非實作。

---

## 第三步：宣告代價

`SPEC.md` §1.1 的 G1／G2／G3 三個能力互相拉扯（`EVAL.md` §1.4 說得更直接：訓練「更主動」會直接傷害「懶得回」）。

因此每一列溯源表 MUST 附一句：**這個改動預期會傷到哪個 suite？**

- 說得出來 → 那個 suite 進驗收清單，改完 MUST 一起看。
- 說「不會傷到任何 suite」→ 可以，但 MUST 說明為什麼這件事是免費的。多數時候答不出來，代表還沒想清楚。
- **MUST NOT 略過這一欄。** `EVAL.md` §12 反模式第 8 條就是「S1 提升就宣告成功，不看 S3」。

---

## 第四步：任務結束時複查

MUST 把溯源表拿出來逐列對照實際的 diff。

| 對照結果 | 處理 |
|---|---|
| 表上有、做了 | 正常 |
| 表上有、沒做 | 明說沒做，不得靜默略過 |
| **表上沒有、但做了** | **scope 溢出** |

scope 溢出的處理 MUST 是下列之一，不接受第三種：

1. 另開任務，重新走一次溯源（若它其實有規格依據）。
2. 從這次 diff 中移除。

「反正已經寫好了」不是理由。已經寫好的錯東西比還沒寫的錯東西更貴，因為它會被後續程式碼依賴。

---

## 中途追加需求

使用者在任務進行中說「還有」「順便」「另外」時：

- MUST NOT 直接接著寫。
- MUST 回到第二步，為追加項單獨產一列溯源。
- 若追加項無 SPEC 條號 → 明說這一點，問要不要先補規格。
- 若追加項會讓 `SPEC.md` §12「明確排除（v1 不做）」清單中的項目變得「順便可以做」→ **MUST 拒絕**。誘因越強越要拒絕；§12 就是為了擋住「順便」而存在的。

---

## 長對話的處理

context 每長一段，原始目標的權重就低一分。

- 每完成一個溯源列，MUST 重述一次原始任務目標再繼續。
- 對話長到需要往回捲才找得到溯源表時，MUST 把溯源表寫進檔案（例如任務分支的 commit message 草稿），然後**建議開新對話**。
- 開新對話時帶的是溯源表與 diff 摘要，不是整段對話歷史。

---

## 反模式

1. 用先前對話的摘要代替讀規格（會漏掉「不是」條款）
2. 溯源表一列寫三件事（合併之後就無法個別複查）
3. EVAL 觀測點欄填「整體品質」「使用者體驗」（不是觀測點，是形容詞）
4. 「先實作，規格之後補」（規格之後不會補；而且事後補的規格會長成實作的形狀）
5. 為了通過溯源而找一個勉強沾邊的條號（比找不到條號更糟——它讓缺口消失在紀錄裡）
6. 任務結束不複查（漂移只在複查時可見）
7. 把 §11 阻塞項當成「大概會這樣」來實作
